# Unnnic Constitution

Unnnic (`@weni/unnnic-system`) is Weni's Vue 3 design system, published to npm
and consumed by many product frontends. This constitution merges the VTEX CX
engineering root principles with the frontend domain principles and instantiates
them for this library. Root principles prevail over domain principles; the
project layer only specializes them.

## Core Principles

### I. Version Control and Review

All code MUST enter `main` through a pull request. A merge MUST require at least
one approved review and a green CI run (`.github/workflows/ci.yaml`: lint,
tests with coverage, build). Direct pushes to `main` MUST be blocked through
GitHub branch protection. Feature work SHOULD be split into small stacked
branches (Graphite) so each pull request stays reviewable.

**Rationale:** the policy is only real when the platform enforces it. Peer review
and a protected `main` keep history auditable and stop unreviewed changes from
being published to npm, since a version change on `main` triggers
`npm-publish.yaml`.

### II. Security and Secrets

Secrets MUST never be committed. Secrets (for example `NPM_TOKEN`,
`CODECOV_TOKEN`, `ROLE_ARN`) MUST come from GitHub Actions secrets or an external
secrets manager (AWS SSM for the localization pipeline) and be injected at
runtime. Access MUST follow least privilege by default. Dependencies MUST come
only from trusted registries (npmjs) and MUST be checked for known
vulnerabilities before release. User-provided content rendered by components
MUST be sanitized (`src/utils/sanitize`) and MUST NOT be injected as raw HTML
without sanitization.

**Rationale:** leaked credentials and untrusted dependencies are among the most
common and most damaging breaches. A design system is a supply-chain dependency
of every consumer, so a compromise here spreads to all of them.

### III. Observability

Logs MUST be structured and MUST never contain secrets or sensitive personal
data. Library code MUST NOT log the content of user input (search text, message
bodies, contact data). Console output MUST be limited to development warnings
that name the component and the misuse. Errors MUST be traceable across
components: they MUST be surfaced to the host application through emitted
events, rejected promises or thrown errors that carry the component context, so
the host's tracing (correlation or trace identifiers) can attach to them.

**Rationale:** structured, privacy-safe telemetry makes incidents diagnosable
without creating new data-exposure risks. The library does not own a tracing
backend, so it MUST give the host enough context to correlate.

### IV. Versioned Contracts

The public interface of this library is everything a consumer can depend on:
exported components and their names, props, emitted events, slots and slot
props, exposed instance members (`defineExpose`), exported composables and
types, SCSS and CSS tokens, the global CSS classes they rely on, and the
`exports` map in `package.json`. Any change to this interface MUST be versioned
following SemVer in `package.json`. Changes MUST be backward compatible, or MUST
ship with an announced deprecation path (marked in the changelog under
Deprecated, kept for at least one minor release). Silent breaking changes MUST
NOT be introduced. Pre-releases MUST use the `-alpha.N` prerelease channel
(`*.*.*-staging` tags → `npm-publish-pre-release.yaml`). Additive features MUST
keep existing renders unchanged; existing snapshot tests are the evidence.

**Rationale:** consumers pin and upgrade this package on their own schedule.
Explicit versioning and deprecation give them a predictable path to adapt
without outages across every product that uses the design system.

### V. Specification Traceability

An engineering spec either derives from a product spec or originates in
engineering. Both are regular paths of the process; neither requires a
justification, and either may follow the full or the lite cycle.

When the change has a product spec, the engineering spec MUST derive from
exactly one approved product spec and MUST reference it through an immutable,
pinned version (commit or tag); a mutable URL or ID alone MUST NOT be used. The
product spec MUST exist and be tagged before its engineering spec is created. An
engineering spec MUST NOT redefine the "what" it inherits: problem, scope,
success criteria and binding decisions belong to the product spec. A technical
architecture document SHOULD be produced for non-trivial features; when it
exists it MUST be linked from the engineering spec, also pinned by commit or
tag, but its absence MUST NOT block the engineering spec. When this library
implements a slice required by another repository's engineering spec (for
example a component contract), the spec in this repository MUST pin that
upstream spec as well.

An engineering spec derived from a product spec MUST open with an inheritance
section in exactly this format:

```
## Inheritance from Product Spec
- Product Spec: <title> — <URL>
- Pinned version: <commit/tag>
- Architecture doc: <none | URL + commit/tag>
- Inherited binding decisions: <short list>
- Scope of this spec: <slice implemented by this repo>
- Divergences: <none | link to amendment>
```

An engineering spec without a product spec states its own "what" and MUST open
with an origin section in exactly this format:

```
## Origin Without Product Spec
- Product Spec: none
- Problem: <what is wrong or missing, in one or two sentences>
- Acceptance criteria: <observable outcomes that prove the change is done>
```

Engineering specs live under `specs/<feature>/` and are produced with the Spec
Kit workflow (`/speckit.specify`, `/speckit.plan`, `/speckit.tasks`).

**Rationale:** traceability from intent to technical execution keeps decisions
auditable. Pinning the product spec version guarantees that every repository
implements the same version of the feature. When the change is born in
engineering (a fix, technical debt), the spec itself is the origin, and its
problem and acceptance criteria are what the change is verified against. A fixed
opening format keeps the origin machine-checkable across repositories.

### VI. No Silent Divergence

When a technical need contradicts something inherited from the product spec
(scope, success criteria or a binding decision), the divergence MUST NOT be
implemented silently in code. It MUST be raised as an amendment in the product
repository and recorded in the `Divergences` field of the engineering spec's
inheritance section, linking to that amendment. Once the amendment is approved
and produces a new tag, the engineering spec's `Pinned version` MUST be updated
to it. A technical difference that contradicts nothing inherited is not a
divergence but an implementation decision, and MUST live in the engineering
spec. This principle applies only to engineering specs derived from a product
spec.

**Rationale:** in a federated model where the product spec is the single source
of truth, a silent code deviation makes intent and implementation drift apart
with no audit trail. Amendments keep the spec authoritative and every decision
traceable to an agreed change.

### VII. Commit Messages

Commits MUST follow Conventional Commits: `<type>: <description>`, optionally
with a scope, `<type>(<scope>): <description>`. Allowed types: `feat`, `fix`,
`docs`, `refactor`, `test`, `chore`. In this repository the scope SHOULD name
the affected component or area (`feat(MultiSelect): …`, `chore(speckit): …`).
The description MUST be imperative, specific and no longer than 50 characters.
Commits MUST be atomic: one logical change per commit.

**Rationale:** conventional commits enable automated changelog generation and
semantic versioning. Atomic commits simplify bisecting, reverting and reviewing.

### VIII. Changelog Maintenance

`CHANGELOG.md` MUST follow the Keep a Changelog format. Every user-facing change
(any change to the public interface defined in Principle IV, visual changes to a
component, or behaviour fixes) MUST appear under the appropriate category:
Added, Changed, Deprecated, Removed, Fixed, Security. Entries MUST name the
component in bold (`- **UnnnicMultiSelect**: …`). Version headings MUST match
the SemVer version in `package.json`; unreleased changes MUST be listed under an
`Unreleased` heading until the release commit assigns the version.

**Rationale:** the changelog is the release documentation consumers read before
upgrading. SemVer alignment sets predictable upgrade expectations.

### IX. Code as Documentation

All code MUST be written in English, including identifiers, comments,
documentation and Storybook descriptions. Domain terms or acronyms that only
have meaning in the original language MAY remain untranslated; sample data in
stories MAY use the product's language. Code MUST prioritize readability and
clarity over brevity. Every non-trivial decision MUST be documented with a
comment that explains the "why", not the "what".

**Rationale:** a globally readable codebase supports open-source contribution
(this repository is public) and cross-team collaboration. Comments that explain
reasoning protect invariants future developers cannot see.

### X. Type Safety

All new files MUST be written in TypeScript (`.ts`, or `.vue` with
`<script setup lang="ts">`). JavaScript files SHOULD only be modified for bug
fixes or small changes; substantial modifications SHOULD include migration to
TypeScript. Test files and stories MAY remain JavaScript, matching the
surrounding files. Type definitions MUST be explicit for public interfaces
(props, emits, slots, exposed members, exported composables and types); `any`
SHOULD be avoided except when interfacing with untyped external libraries.
Strict mode MUST be enabled in `tsconfig.json`, and `npm run type-check`
(`vue-tsc --noEmit`) SHOULD pass for changed files.

**Rationale:** static typing catches errors at compile time and is the
documentation consumers see through the generated `.d.ts` files. Gradual
migration allows incremental adoption without blocking delivery.

### XI. Single Responsibility

Each file SHOULD contain no more than 350 lines of code. Each function MUST have
one responsibility. Template logic MUST be extracted to computed properties or
methods to keep markup declarative. Complex conditional rendering MUST be
abstracted into descriptive boolean variables. Logic shared by several
components, or that would push a component past the size limit, SHOULD move to
a composable in `src/composables/`.

**Rationale:** small, focused units are easier to test, review and refactor.
Readable templates make a component's visual structure immediately apparent.

### XII. Naming Conventions

Variable and function names MUST use `camelCase`. Component names MUST use
`PascalCase` and, for public components, MUST carry the `Unnnic` prefix
(`defineOptions({ name: 'UnnnicMultiSelect' })`). File and directory names MUST
be lowercase (camelCase where the existing convention uses it, for example
`useSelectBase.ts`, `pt_br.json`), with the exception below. Abbreviations MUST
be avoided unless universally understood; clarity MUST take precedence over
conciseness.

**Project exception:** component folders and component single-file components
under `src/components/` stay `PascalCase` (`MultiSelect/index.vue`,
`Checkbox/Checkbox.vue`, `MultiSelect/MultiSelectOption.vue`). Every other path
(composables, utils, types, SCSS, locales, stories, tests) MUST follow the
lowercase rule. Justification: about 70 existing component folders use
PascalCase, consumers import some `src/` paths directly from the published
package, and renaming them would be a breaking change under Principle IV with no
benefit to consumers.

**Rationale:** consistent naming reduces cognitive load and makes the codebase
searchable. The exception keeps the public import paths stable.

### XIII. Component Architecture

Components MUST be named descriptively and reflect their purpose. Related
components SHOULD be grouped in the same folder (a component and its
subcomponents, for example `MultiSelect/` with `MultiSelectOption.vue`).
Primitives built on headless libraries SHOULD live in `src/components/ui/`.
Public components MUST be exported from `src/components/index.ts` under their
`Unnnic` name. Props MUST have descriptive names (`itemLabel`,
`infiniteScrollDistance`). Listener props and handler functions received by a
component MUST be prefixed with `on` (`onUserEmailChange`). Methods that handle
state updates SHOULD be prefixed with `handle` (`handleSelectOption`). State
variables MUST clearly reflect what they represent (`isLoadingUser`,
`isSearchActive`).

**Project exception:** emitted event names follow Vue convention and are
declared without the `on` prefix in `defineEmits` (`update:modelValue`,
`update:search`, `scroll-end`). Two-way bindings MUST use `update:<prop>` so
`v-model` works. Justification: Vue adds the `on` prefix to the listener
automatically, and `v-model` depends on the `update:*` names; prefixing the
emitted name would break `v-model` and the existing public events.

**Rationale:** a predictable component structure makes the library navigable.
Clear naming for props, events and state makes component interfaces
self-documenting for consumers.

### XIV. Styling Standards

CSS selectors MUST use classes only; IDs MUST be reserved for JavaScript
targeting when no alternative exists. Component styles MUST be `scoped` SCSS
that imports the token entry point (`@use '@/assets/scss/unnnic' as *;`). Nested
selectors SHOULD be avoided to preserve specificity control; `:deep()` SHOULD be
limited to styling child components of the design system itself. Design tokens
MUST be used instead of hardcoded values whenever a token exists: colors
(`$unnnic-color-*`), spacing (`$unnnic-space-*`), icon sizes
(`$unnnic-icon-size-*`), radii, shadows and font mixins. Deprecated tokens
(`$unnnic-spacing-*`) MUST NOT be used in new code.

**Rationale:** tokens are the single source of truth for the visual language and
what lets consumers theme the library. Avoiding IDs and deep nesting prevents
specificity wars in consumer applications.

### XV. BEM Methodology

CSS class names MUST follow BEM. Blocks MUST be independent components and MUST
carry the `unnnic-` prefix (`.unnnic-multi-select`). Elements MUST be parts of a
block and use double underscores (`.unnnic-multi-select__options`). Modifiers
MUST represent variations and use double hyphens
(`.unnnic-multi-select-option--level-2`). Elements MUST NOT be nested in class
names (`.block__elem`, not `.block__elem1__elem2`).

**Rationale:** BEM gives scoped, collision-free CSS. The `unnnic-` prefix keeps
the library's classes from colliding with the consumer application's own CSS.

### XVI. State Management

Unnnic is a component library and MUST NOT ship a global store. Shared state
MUST belong to the host application and reach components through props and
`v-model`. State MUST NOT be duplicated between a component and its props: a
component MUST derive from its props and emit changes instead of keeping a
parallel copy, unless it intentionally owns an uncontrolled value. Local
component state SHOULD be preferred for purely visual state (open, focused,
expanded). Library-wide singletons that already exist (for example
`unnnicToastManager`) MUST stay the only source of their state.

**Rationale:** a controlled-component model keeps data flow traceable for
consumers and prevents the synchronization bugs that come from duplicated
state.

### XVII. Async State Correctness

Async operations (loading more options, uploads, asynchronous validation) MUST
track loading, success and error states consistently and expose them to the
consumer (props, events or exposed members). Silent failures MUST NOT occur;
errors MUST be surfaced to the consumer or the user. Contradictory states (for
example loading and error at the same time) MUST be prevented. Double triggers
(for example repeated `scroll-end` emissions while loading) MUST be guarded
against. State rollback MUST occur when an operation fails after an optimistic
update.

**Rationale:** incorrect async state is one of the most common sources of broken
UX. Users must always know what is happening.

### XVIII. API Integration

Components MUST NOT call product backends; data MUST reach them through props,
slots or callbacks provided by the consumer. Where the library itself needs I/O
(for example loading icons or assets), the call MUST be encapsulated in a
dedicated module in `src/utils/` or `src/lib/`, separate from components. Error
handling MUST be explicit; errors MUST NOT surface as unhandled exceptions.
Loading and error states MUST be tracked and reflected in the UI.

**Rationale:** a design system that knows no backend stays reusable by every
product. Isolating the few I/O paths it has keeps components focused on
rendering and easy to test.

### XIX. API and Data Boundaries

Backend contracts MUST stay outside the library. Internal code and public props
MUST use camelCase. Components MUST NOT require backend field names; mapping
keys MUST be configurable through props (as `itemLabel` and `itemValue` do)
instead of hardcoding snake_case fields. Raw backend shapes MUST NOT leak into
composables or components. Types that intentionally mirror an external contract
MAY use that contract's naming.

**Rationale:** clean data boundaries prevent coupling the library to one
product's backend and keep it usable by all consumers.

## Quality Standards

### XX. Testing

Components and composables with logic MUST have unit tests (Vitest with
`@vue/test-utils`). Test files MUST be colocated in a `__tests__/` subdirectory
next to the code they test. Tests MUST verify behavior and outcomes, not
implementation details. Tests MUST NOT be added solely to raise coverage; they
MUST validate real user behavior. A test that would still pass after a
regression MUST be fixed or removed. Snapshot updates MUST be intentional and
explained in the pull request; an additive change MUST NOT alter existing
snapshots. Every public component SHOULD have a Storybook story in
`src/stories/` that documents its props and the new behaviors added.

**Rationale:** colocated, behavior-focused tests survive refactors. Snapshots are
the guard for Principle IV, so unexplained snapshot churn hides breaking
changes.

### XXI. Accessibility

Interactive elements MUST be keyboard accessible (the select family shares
`useSelectKeyboard`). Form inputs MUST have associated labels or an accessible
name. Composite widgets MUST expose the matching ARIA roles and states (for
example `role="tree"` / `treeitem` with `aria-level`, `aria-expanded`,
`aria-checked`). Color MUST NOT be the only means of conveying information.
Images MUST have meaningful `alt` text or be marked decorative with `alt=""`.
Focus states MUST be visible.

**Rationale:** accessibility is a legal requirement in many jurisdictions.
Fixing it once in the design system fixes it in every product that uses it.

### XXII. Performance

Unused dependencies MUST be removed. Heavy computations MUST be memoized
(`computed`) or debounced when executed on frequent events. Assets MUST be
optimized (images, fonts, SVG icons). The bundle size impact of a new dependency
SHOULD be evaluated before adding it, and per-component imports (README,
"import on demand") MUST keep working. Initial render SHOULD avoid work that is
only needed after interaction (for example rendering popover content before it
opens).

**Rationale:** every kilobyte here ships in every consumer. Keeping bundles lean
and computations efficient protects users on slow networks and devices.

### XXIII. Internationalization

User-facing strings MUST NOT be hardcoded; they MUST be externalized to locale
files and read through i18n (`$t`). Date, number and currency formatting MUST
respect the user's locale. Locale files SHOULD keep parity across all supported
languages.

**Project exception (localization lock):** new and changed strings MUST be
written only to the source file `src/locales/en.json` (the `source` in
`crowdin.yml`). Translation files (`src/locales/pt_br.json`,
`src/locales/es.json` and any other file matching the Crowdin `translation`
pattern) are managed by the Localization team through Crowdin and MUST NOT be
created, modified or deleted in feature work; the `.githooks/pre-commit`
localization lock and the `localization-automation.yml` workflow enforce this.
Translations are therefore delivered after merge by the localization pipeline,
not before merge. Justification: the organization's localization golden path
makes Crowdin the single owner of translations; editing them in feature
branches would create conflicting sources of truth.

**Rationale:** externalized strings enable translation without code changes, and
a single owner for translations keeps quality consistent across languages.

### XXIV. Defensive Programming

Defensive guards (null checks, fallback branches, runtime assertions) SHOULD
only be added when the invalid state is realistically reachable, for example
props a consumer can omit or pass in an unexpected shape. Root causes MUST be
fixed rather than masked with defensive code. Guards MUST follow the patterns
already established in the surrounding code.

**Rationale:** unnecessary defensive code obscures real logic. Guards should
protect against realistic consumer misuse, not hypothetical cases.

### XXV. Maintainability

Business and behavior rules MUST NOT be duplicated across components; they MUST
be centralized in a single source of truth (for example shared select logic in
`useSelectBase`, `useSelectKeyboard` and the shared SCSS partials). Local
duplication of utility code MAY exist when extraction would create unnecessary
coupling. Abstractions SHOULD only be created when there is a clear pattern
across multiple use cases.

**Rationale:** not all duplication is harmful; premature abstraction creates
coupling that is worse than the duplication it removes. Centralize rules,
tolerate incidental duplication.

## Project Constraints

- **Stack:** Vue 3 (`^3.4.8`, peer dependency), TypeScript, SCSS, Vite library
  build, Style Dictionary for tokens, reka-ui and vaul-vue for headless
  primitives, vue-i18n.
- **Layout:** components in `src/components/<Component>/`, composables in
  `src/composables/`, tokens and SCSS in `src/assets/scss/`, locales in
  `src/locales/`, stories in `src/stories/`, shared types in `src/types/`.
- **Quality gates (CI on every push):** `npm run lint`, `npm run coverage`
  (Vitest), `npm run build`. Code MUST pass ESLint with the
  `@weni/eslint-config` Prettier rules (single quotes, trailing commas, 80
  columns, one attribute per line).
- **Release:** stable versions publish from `main` when `package.json` changes
  (`npm-publish.yaml`); pre-releases publish from `*.*.*-staging` tags on the
  `alpha` dist-tag (`npm-publish-pre-release.yaml`).
- **Runtime guidance:** `AGENTS.md` (localization lock) and the Spec Kit skills
  in `.cursor/skills/` complement this constitution and MUST NOT contradict it.

## Governance

This constitution supersedes other engineering practices in this repository.
Amendments MUST be made through a pull request that updates this file, records a
Sync Impact Report and bumps the version. Changes inherited from
`weni-ai/vtex-cx-engineering-constitutions` MUST be brought in by re-running
`setup-engineering`, not by editing inherited articles by hand.

Versioning follows SemVer for governance: MAJOR when a principle is removed or
redefined incompatibly, MINOR when a principle or section is added or materially
expanded, PATCH for clarifications and wording fixes.

Compliance: every plan (`/speckit.plan`) MUST pass a Constitution Check against
these principles, and any deviation MUST be justified in the plan's complexity
tracking. `/speckit.analyze` MUST treat a conflict with a MUST statement as
CRITICAL. Reviewers MUST verify compliance in pull requests. A project exception
is valid only when written in the article it relaxes, with its justification.
